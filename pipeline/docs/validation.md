# 사용자 흐름 구현 검증 기록

검증일: 2026-11-12. 작업 브랜치: `db`. 운영 데이터와 기존 볼륨·체크포인트는 사용하거나 변경하지 않았다.

## 자동 검사

- 전용 파이프라인 검사: 최종 25개 통과. 계산 기대값, 공유 계정·탭, 체류 종료·관측 공백, 지연 성공, 역방향 이동, 원본 누락·내용 불일치·위치 중복, 공개 실패, 청크 재조립·재처리·충돌, 만료·보존 경계 등을 포함한다.
- QA 전체 회귀 검사: 217개 통과. QA 코드·테스트 수정 없음.
- 파이프라인과 QA를 병렬 재검사했을 때 기존 동시 입장 부하 테스트가 한 번 실패했다. 기대 동시 입장 60명에 관측 41명이었고, 해당 파일 단독 재검사에서는 7개 모두 통과했다. 기대값이나 QA 코드는 변경하지 않았다. 시간 의존 검사이므로 이 이력을 숨기지 않는다.
- 이후 다른 부하 없이 QA 전체를 단독 재실행하여 217개 통과를 최종 확인했다.
- 실행 Python: 격리 가상환경 3.12.14. 저장소의 QA 배포 요구 버전은 3.13 이상이므로 동일 배포 버전 검증을 대신하지 않는다.
- 자동 만료 인덱스 생성 옵션은 단위 시험으로 확인했다. 실제 서버의 TTL 삭제 지연이나 읽기 전용 역할 권한 강제 시험은 수행하지 않았다.

## 실제 Kafka·Spark·MongoDB 시험

`pipeline/tests/compose.integration.yml`로 별도 시험 프로젝트를 생성했다. 기존 운영 네트워크·DB·볼륨을 연결하지 않았고 공개 포트도 만들지 않았다.

구성:
- Kafka: 로컬 `apache/kafka:4.1.2`, 토픽 1개·파티션 1개.
- 원본 적재: 기존 원본 소비 루프와 라우팅·쓰기 코드를 그대로 가져온 격리 작업. 그룹 `ticketguard-raw-db-v1`.
- Spark: 로컬 `ticket-guard-workspace-spark:dev`, `local[2]`, 새 코드 읽기 전용 마운트. 그룹 `ticketguard-spark-consumer`.
- MongoDB: `mongo:8.0.34`, 임시 메모리 저장소에 원본·지표 DB 분리. 시험용 무인증 내부 네트워크이며 운영 설정으로 사용하면 안 된다.
- 입력: 같은 계정을 공유하는 브라우저 식별자 10개, 각 회차 40개 이벤트, 3회 총 120개, 청크 비율 0%.
- 이벤트는 준비 완료 후 묶음으로 전송했다. 일정한 초당 입력을 유지한 장시간 부하 시험이 아니다.
- 측정: 합성 `receivedAt` 생성 직전부터 검증된 공개 문서를 0.1초 간격으로 관측할 때까지. 실제 웹 수집 서버·관리자 화면을 거친 측정이 아니다.

초기 소규모 시험:

| 회차 | 검증 공개 관측까지 |
|---|---:|
| 1 | 2.649초 |
| 2 | 1.147초 |
| 3 | 1.136초 |

12시간 결측 격자와 최종 시계열 저장 구조 반영 후 재시작 시험:

| 회차 | 검증 공개 관측까지 |
|---|---:|
| 1 | 6.349초 |
| 2 | 1.248초 |
| 3 | 1.654초 |

첫 회차는 재시작 후 이전 공개 포인터가 남은 상태에서 전송해 준비·재처리 구간이 포함됐다. 세부 Spark 기동·재처리·조회 시간을 분리 측정하지 않았으므로 초과 원인을 단정하지 않는다. **한 회차가 5초를 초과했으며 전체 5초 목표는 미달·미확정이다.** 화면 시간을 제외한 값이므로 운영 목표 달성으로 보고하지 않는다.

청크, 재처리, 실패 복구의 다수 조합은 단위 시험으로 검증했으며 실제 Kafka 통합 시험에서 모두 재현한 것은 아니다.

## 모의 처리·저장 크기

`benchmark_flow.py` 초기 측정에서 브라우저 100개·합성 이벤트 400개의 메모리 모의 DB 처리·검증·저장은 1.1923초였다. 두 시계열을 각각 8,640개 관측값으로 만든 BSON 구조는 약 2,039,348바이트였다. 이는 실제 Kafka 처리 성능이나 최대 상태 처리 성능이 아니다.

최종 구현은 요약 문서에서 시계열을 분리해 중복 저장을 줄였다. 시계열 불변 버전 전체를 기록하므로 30초 유예 기간의 이전 버전 비용이 추가된다. 실제 차원 수와 갱신 빈도로 저장량을 확인해야 한다. 단순히 8,640개 시점만 저장된다고 총 저장량을 계산하면 안 된다.

## 남은 제한

1. 12시간 누적 최대 부하와 관리자 화면을 포함한 5초 목표는 아직 검증하지 못했다. 목표 부하에 대한 합의가 필요하다.
2. 로컬 파생 관측 재계산 구조라 상태·차원 수가 증가하면 처리 시간이 증가한다. 기본 상태 250,000개, 차원 100개, 문서 8MiB 제한을 넘으면 공개를 차단한다. 고부하 분산 실행이나 대상별 증분 집계로 확장하려면 후속 구현이 필요하다.
3. 목록·상세 화면의 무활동 접속은 기존 수집만으로 정확히 유지할 수 없다. 30초 활동 기준 추정이며 웹 영역 보완이 필요하다.
4. 현재 필터는 전체와 관측된 완전 일치 차원 조합이다. 공연 단독 등 임의 조합의 정확한 평균·중앙값 계산은 별도 계약이 필요하다.
5. 읽기 전용 공개 뷰·권한 생성 스크립트를 제공했지만 운영 계정·권한을 변경하지 않았다.
6. 원본의 보존 범위를 넘는 재계산·미완성 청크의 자동 건너뛰기 도구는 없다. 오류 후 같은 체크포인트로 재시작하거나 별도 격리 재계산 절차를 따른다.

관리자 화면은 수정하지 않았으며 커밋·푸시도 수행하지 않았다.

## 디렉터리 정리 후 확인

환경 설정, 기존 적재, 사용자 흐름, DB 권한, 점검 도구, 문서를 별도 폴더로 이동하고 Python 가져오기와 Docker 복사 경로를 수정했다. 지표 계산과 저장 규칙은 이번 정리에서 변경하지 않았다.

- 로컬 모듈 가져오기와 Python 문법 검사 통과.
- 별도 `layout-check` 태그의 Docker 이미지 빌드 통과.
- 외부 네트워크와 DB 없이 실제 Spark 작업자 모듈 확인 통과.
- QA 전체 회귀 검사 217개 통과.
- 파이프라인 전용 테스트 폴더는 정리 작업 시작 시 이미 없었으므로 복원하거나 재실행하지 않았다. 앞의 25개 통과 기록은 이전 구현 시점의 이력이다.
- 운영 컨테이너와 기존 데이터·체크포인트는 변경하지 않았다.
