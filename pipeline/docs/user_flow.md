# 사용자 흐름 지표 처리

## 범위와 실행 모드

`main.py flow`가 새 처리 경로다. 기존 `ingest`와 `check`는 유지한다. `tools/resolve_dependencies.py`는 빌드 의존성 확인만 수행한다. 기존 `ingestion/mongo_writer.py`의 누락된 `normalize`는 별도 `ingestion/normalization.py`로 보완했다. 기존 적재 모드는 청크를 `chunk_requires_flow_mode` 사유로 분류하며, 청크 재조립과 검증 공개는 새 `flow` 모드가 담당한다.

관리자 코드, QA 공용 코드, 웹 수집 코드, 기존 원본 적재 코드는 수정하지 않았다. 운영 환경에 새 처리를 자동으로 연결하지 않는다.

## 처리 구조

1. 기존 원본 적재기는 기존 그룹으로 원본을 별도 DB에 적재한다.
2. Spark는 별도 그룹으로 같은 토픽을 읽는다. 최대 100개씩 순회하여 원본 DB의 아홉 라우팅 컬렉션을 위치 인덱스로 조회한다.
3. 원본의 `source/topic/partition/offset`과 소비한 레코드의 바이트가 일치해야 한다. 위치 중복, 내용 불일치, 누락은 공개를 차단한다. 파티션의 최소·최대 오프셋은 대조한 범위의 외곽이며 중간의 모든 정수 위치가 존재한다는 보장은 아니다.
4. 이벤트 해석과 청크 재조립 후 본문을 버리고 최소 관측값만 체크포인트 옆에 기록한다.
5. 소비 경로와 원본 경로의 독립된 파생 상태에서 지표를 다시 계산해 대조한다. 계산기는 공유하므로 별도의 수작업 기대값 테스트로 계산식도 검증한다.
6. 검증된 최신 수치와 그래프, 시계열을 불변 버전 문서로 기록한다. 공개 포인터 교체가 마지막 동작이다. 실패한 임시 버전은 읽기 전용 공개 뷰에서 보이지 않는다.
7. 타이머가 새 이벤트가 없는 시간에도 접속 만료와 시계열을 갱신한다. 미완료 배치나 청크가 있으면 공개하지 않는다.

원본 DB에는 읽기만 수행한다. 원본 인덱스는 기존 `raw_kafka_position_v1`을 사용하며 운영 인덱스를 자동 변경하지 않는다. 관리자 읽기 계정은 원본 DB에 접근할 필요가 없다.

## 상태 저장과 제한

현재 저장 구현은 단일 `local[2]` Spark 전용이다. 분산 클러스터에서는 시작을 거부한다. 파티션 단위 원본 스트리밍 순회는 사용하지만 최소 관측값의 계산은 로컬 처리다. 대규모 분산 집계가 구현되었다고 간주하면 안 된다.

`FLOW_CHECKPOINT_DIR` 아래에 Spark 오프셋 체크포인트와 두 개의 SQLite 파생 상태를 함께 둔다. 기존 체크포인트와 다른 경로를 사용한다. 이는 QA DB를 SQLite로 되돌리는 작업이 아니라, 원본을 중복 저장하지 않으면서 정확한 중앙값·늦은 순서·원본 대조 상태를 복구하기 위한 처리 전용 로컬 상태다.

두 상태 DB에는 식별자, 단계, 활동·수신 시각, 성공·취소 여부, 내용 지문만 남긴다. 요청·응답 본문은 저장하지 않는다. 청크 본문만 재조립 완료 전까지 임시 보관한다. 합성 관측 상태는 기본 각각 최대 250,000개, 청크 조각은 최대 4,096개, 논리 이벤트는 최대 8MiB다. 초과하면 누락시키지 않고 중단한다.

현재 계산은 보존 범위 안의 최소 관측값을 로컬에서 재계산한다. 원본 전체나 지표 DB 전체를 스캔하지는 않지만 누적 자료 수와 차원 수에 비례해 비용이 증가한다. 따라서 현재 코드는 제한된 로컬 시뮬레이션용이며, 최대 1시간 부하에서 5초를 달성했다는 보장은 없다. 장시간 고부하에는 대상별 증분 기여도·중앙값 상태 구조를 추가해 검증해야 한다.

원본 비교는 한 번에 최대 100개이고 기본 처리 주기는 1초다. 원본 대기는 `FLOW_RAW_WAIT_SECONDS`의 기본 10초 상한 안에서 0.25초 간격으로 재시도한다. 계속 실패하면 스트리밍을 실패시켜 공개를 보류한다. 원본 적재를 복구한 뒤 같은 체크포인트로 재시작하면 해당 배치를 다시 처리한다. 처리 지연 목표를 의미하지 않는다.

## 지표 정의

집계 단위는 `pageInstanceId`로 식별한 브라우저 세션이다. 공유 계정은 합치지 않는다. 이 값은 세션 저장소 기반이므로 탭 복제 등으로 식별자가 복제되면 구분하지 못할 수 있다. 브라우저 식별자가 없는 서버 자료는 예매율에는 사용할 수 있지만 접속 인원에는 포함하지 않는다. 익명 쿠키를 탭 식별자와 동시에 세어 인원을 부풀리지 않는다.

서버 업무 이벤트와 성공한 heartbeat 응답은 서버 단계를 반영한다. `page_enter`는 실제 화면 단계를 반영한다. 발생 시각 순서로 최신 단계를 대표 단계로 선택한다. 동시간 관측은 이벤트 식별자 순서로 결정한다. 이는 서버 단계와 화면 단계의 지연을 완전히 해소하는 정책은 아니므로 시뮬레이션 관측 한계로 남긴다.

- 단계: `shows/detail/queue/captcha/select/complete/other`.
- 접속: 최근 활동 후 기본 30초 미만이며 명시적 이탈·취소·타임아웃이 없는 브라우저. 정확한 소켓 연결 수가 아니라 추정 활동 접속 수다.
- 체류: 최근 1시간 안에 시작한 단계 방문 중 종료가 관측된 표본의 초 단위 평균·중앙값. 다음 단계, 명시적 화면 종료 또는 취소로 닫는다. 타임아웃은 정확한 종료 시각으로 삼지 않는다.
- 진행 중 체류는 완료 통계에서 제외한다. 표본이 없으면 평균·중앙값은 `null`이다.
- 이동률: 최근 1시간에 출발 단계를 관측한 고유 단위 중 바로 연결된 이동이 관측된 단위의 비율. 단위는 예매 시도이며 시작 전에는 동일 브라우저의 다음 시작 시도에 연결하고, 연결할 시도가 없으면 브라우저다. 건너뛴 단계를 임의로 채우지 않는다.
- 같은 방향의 반복 이동은 단위별 한 번만 계산한다. 반복 방문의 체류 표본은 각각 계산한다.
- 예매율: 최근 1시간에 시작한 고유 예매 시도 중 서버 성공이 확인된 비율. `queue_enter/queue_register`는 하나의 시작이며 재전송은 추가 성공이 아니다.
- 시간별 예매율: 시작 시각을 5초 구간에 넣고 후속 성공을 해당 시작 구간에 반영한다. 비율 단위는 0~1이다.
- 현재 인원과 단계별 인원 합계는 동일하다. 기타·미확인 단계도 포함한다.

목록·상세에는 공통 heartbeat가 없으므로 장시간 조작 없는 방문은 30초 후 비활성으로 추정된다. 정확한 접속을 원하면 웹 담당 영역에서 주기적 접속 신호를 보완해야 한다. 이 작업은 웹 코드를 변경하지 않는다.

첫 번째 버전의 서버 시도 이벤트에서 확인한 시뮬레이션·공연·회차를 같은 시도의 캡처 이벤트에 연결한다. 두 번째 버전의 캡처만 있고 근거가 없으면 시뮬레이션 구분은 미확인이다. 미확인을 정상으로 간주하지 않는다.

## 실행과 설정

`configuration/flow.env.example`을 참고해 무시되는 별도 환경 파일을 작성한다. 비밀번호는 주소에 맞게 인코딩한다. 지표 DB는 기존 시스템 DB와 다른 `ticketguard_flow`를 권장한다. 기존 계정·볼륨을 변경하지 않는다.

```powershell
docker compose --env-file .env.flow -p ticket-guard-flow -f compose.flow.yml up -d --build
docker compose --env-file .env.flow -p ticket-guard-flow -f compose.flow.yml logs --tail 50 flow
```

실행 전 기존 Kafka, 원본 DB, 지표 DB의 네트워크 이름을 확인한다. 동시에 기존 Spark 작업과 같은 그룹을 사용하지 않는다. 새로운 그룹이 필요하면 명시적으로 설정하되 기존 원본 그룹은 변경하지 않는다.

- `FLOW_RAW_MONGO_URI`: 원본 DB 읽기 전용 연결.
- `FLOW_TARGET_MONGO_URI`: 전용 지표 DB 쓰기 연결.
- `RAW_SOURCE_ID`: 기존 원본 적재기와 정확히 같은 값.
- `FLOW_TRIGGER_SECONDS`: 기본 1초, 설정 허용 상한 60초. 전체 반영 시간 보장은 아니다.
- `FLOW_PRESENCE_SECONDS`: 기본 30초.
- `FLOW_GRACE_SECONDS`: 지연·상태 정리 여유, 기본 300초.
- `FLOW_MAX_EVENTS`: 기본 250,000개. 상한에 맞춰 중단되므로 무제한 처리로 간주하지 않는다.
- `FLOW_CHECKPOINT_DIR`: 새 작업 전용 경로.
- `SPARK_MAX_OFFSETS_PER_TRIGGER`: 기본 1,000개.

청크가 끝내 완성되지 않으면 이후 공개도 보류된다. 조각을 조용히 버리지 않는다. 원본 적재 상태를 먼저 복구하고, 재구성이 필요하면 별도 새 체크포인트와 별도 지표 DB에서 재계산한다. 기존 체크포인트를 삭제해서 해결하지 않는다. 자동 청크 건너뛰기·대규모 과거 재생 도구는 제공하지 않는다.

## 보존

시계열은 최근 1시간의 5초 격자, 시계열당 720개 시점이다. 갱신은 1초마다 진행 중인 5초 구간을 수정하여 구간 종료를 기다리느라 5초 목표를 소진하지 않는다. 마지막 갱신과 기준 시각을 함께 제공한다.

접속 이력의 중단 구간은 `observed=false`, 값은 `null`이다. 재가동 시 누락 구간을 0명으로 만들지 않는다. 예매 시계열도 관측 범위 밖의 구간과 관측된 무시도 구간을 구분한다.

현재 공개 문서는 만료시키지 않는다. 이전 버전과 실패 잔여물은 30초 조회 유예 후 TTL 대상으로 전환한다. 현재 공개 문서의 시계열 내용이 오래되더라도 조회 시 현재 시각 기준 1시간을 다시 적용해야 한다. TTL은 즉시 삭제되지 않는다.

파생 이벤트는 1시간과 300초 여유를 넘으면 비활성 브라우저부터 정리한다. 최근 활동 중인 대상의 이전 시작·진입 근거는 시간만으로 삭제하지 않으며 용량 상한으로 보호한다. 지속 활동이 많으면 상한에 도달할 수 있다. 보존 범위보다 오래된 늦은 이벤트는 조용히 버리지 않고 별도 재계산이 필요하다는 오류로 중단한다.

원본 DB의 보존 정책은 변경하지 않는다.

## 검증 명령

현재 `pipeline/tests/`에는 계산 기대값·원본 대조·복구·공개 검사와 새 격리 통합 시험이 있다. 실행 절차와 관리자 후속 변경은 [실행 준비](connection_work.md)를 따른다. 아래 명령은 QA 회귀 검사다.

```powershell
$env:PYTHONPATH='qa/src'
.venv/Scripts/python.exe -m pytest qa/tests -q -p no:cacheprovider
```

이전 격리 통합 시험과 이번 검사는 별도 수행 기록이다. 현재 재현용 파일은 `pipeline/tests/compose.integration.yml`과 `verify_stream.py`다.
